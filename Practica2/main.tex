\subsection{Consultar los datos relacionados con subdominios de ingenieria.unam.mx}

Utulizando subfinder, se pueden consultar los subdominios
de un dominio en especifico, donde en este caso el comando es el siguiente:

\begin{lstlisting}[style=consolaSeguridad]
  subfinder -d ingenieria.unam.mx -v
\end{lstlisting}

En este caso el comando nos regresa una lista 
de subdominios que pertenecen al dominio de ingenieria.unam.mx, donde se puede observar que
el comando tiene la opción \texttt{-v} que nos permite ver el progreso de la búsqueda de subdominios, 
esto hace que el comando tarda un poco en ejecutarse.

Ejecutando el comando subfinder lo que haces es llamar a la 
dependencia de subfinder para que busque los subdominios del dominio de ingenieria.unam.mx,
ahora bien, este va concatenado con la opción \texttt{-d} 
que indica el dominio que se va a buscar, 
y finalmente la opción \texttt{-v} que indica que se muestre el progreso de la búsqueda.

  \centering
  \includegraphics[width=0.8\textwidth]{img/image3.png}

\begin{figure}[H]

\subsection{Utilice la herramienta httpx para verificar cuales de los dominios identificados por
subfinder corresponden a subdominios activos, es decir, que proporcionan algún
servicio publicado en internet.}

Para utilizar el siguiente comando es: 

\begin{lstlisting}[style=consolaSeguridad]
  httpx -status-code -title -tech-detect -list subdominios.txt
\end{lstlisting}

Este comando lo que hace es 
verificar cuales de los subdomonios identificados 
por subfinder corresponden a subdominios activos, 
es decir, que proporcionan algún servicio publicado en internet.

La forma en que esta colocado el comando es el siguiente: 

\begin{enumerate}
  \item \texttt{-status-code} : Muestra el código de estado HTTP de la respuesta.
  \item \texttt{-title} : Muestra el título de la página web.
  \item \texttt{-tech-detect} : Detecta las tecnologías utilizadas en el
  \item \texttt{-list subdominios.txt} : Especifica el archivo de entrada que contiene la lista de subdominios a verificar.
\end{enumerate}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/imagehttpx.png}
  \caption{Verificación de subdominios activos con httpx.}

A partir de los datos generados por la ejecución de 
\texttt{httpx}, con todos los subdominios que teniamos antes, esto hace 
que se pueda  reducir la lista de 
objetivos a únicamente aquellos con servicios web activos. 

\begin{itemize}
    \item \textbf{Disponibilidad y Códigos de Estado:} La mayor parte de los subdominios responde con un código 200, 
    confirmando que exponen contenido web, ademas de que 
    se dejar ver un gran numero de subdominios que redirigen a otras direcciones, estos son codigos de 301, 302 y 303, 
    utilizadas comúnmente para forzar el enrutamiento hacia HTTPS o hacia portales de autenticación.
    Asimismo, se detectaron accesos restringidos 403 Forbidden 
    en los subdominios \texttt{itpro} e \texttt{it-pro}.
    \item \textbf{Servidores Web y Sistemas Operativos:} Lo que mas se deja ver en servicios, es el aervicio activo 
    de Apache HTTP Server y Nginx, ademas de que casi todo se esta corriendo 
    en distribuciones Linux (CentOS, Ubuntu, Fedora, UNIX genérico), con excepcion de algunas que estan alojadas en Microsoft IIS, esto en windows server.
    \item \textbf{Lenguajes y Aplicaciones Backend:} El lenguaje de programación del lado del 
    servidor esPHP, ademas de que 
    se dejo extraer las versiones que se estan usando, donde la gran parte ya no tienen soporte de vida, 
    estas son PHP 5.4.16, 7.0.33, 7.2.1 y la familia 7.4.x. 
    Ademas de esto, se dejo ver que se esta corriendo python, esto para ser mas eseficio son con Uvicorn y Gunicorn y Node.js.
    \item \textbf{Mecanismos de Proteccion:} 
    En este caso dejo ver que existe la plataforma de Cloudflare, esto en multiplies servicios, 
    dejando ver la implementación de mecanismos WAF

\subsection{Utilice la herramienta nuclei para enviar peticiones web a un subdominio y analizar
su respuesta para identificar las características de la tecnología web usada.}

Utilizando nuclei, el siguiente comando es el siguiente:

\begin{lstlisting}[style=consolaSeguridad]
  nuclei -target ssa.ingenieria.unam.mx
\end{lstlisting}

En este caso vamos analizar el subdominio 
de ssa.ingenieria.unam.mx, donde nuclei nos permite enviar peticiones web a un subdominio y analizar su respuesta para identificar las características de la tecnología web usada.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/imagenuclei.png}
  \caption{Análisis de tecnología web con nuclei en ssa.ingenieria.unam.mx.}
\end{figure}

AL poner el comando de nuclei y que analizara el subdominio 
de \texttt{ssa.ingenieria.unam.mx}, se puede ver toda la parte de seguridad 
donde de manera inicial,
el análisis directamente nos dice lo que el anterior comando nos puso 
que el sitio se encuentra alojado 
detrás de la red de entrega de contenido (CDN) 
y el firewall de aplicaciones web (WAF) de Cloudflare, 
trabajando con un servidor Nginx. 

No obstante, lo que se deja ver despues 
es la parte importante esto por que nuclei identificó 
la habilitación de protocolos de seguridad obsoletos, 
específicamente TLS 1.0 y TLS 1.1, 
ademas de esto, de que usan suites de cifrado catalogadas 
como débiles, las cuales son por poner el ejemplo las 
\texttt{TLS\_ECDHE\_RSA\_WITH\_AES\_128\_CBC\_SHA}. 
Aunque el servidor puede llegar a soportar simultáneamente 
las versiones modernas de TLS 1.2 y 1.3, esto 
mediante un certificado válido de Google Trust Services, teniendo esto en cuenta, el hecho de
mantener activos los protocolos heredados representa un riesgo considerable, ya que expone las comunicaciones a ataques de degradación
que podrían comprometer la información en tránsito.

Finalmente, a nivel de frontend, 
nuclei detectó la ausencia del mecanismo 
de Integridad de Subrecursos, esto por que 
el sitio carga bibliotecas de código de terceros 
como jQuery y FontAwesome desde servidores externos que son los de
Google APIs sin incluir un hash criptográfico de validación. 

Esto lo que podria provar en un futuro es que en caso de que el proveedor externo sufriera una vulneración, permitiría la inyección y ejecución de scripts maliciosos (XSS) 
directamente en los navegadores de los usuarios de la facultad sin que el sitio pueda detectarlo

\section{Actividades:}
\subsection{Actividad 1 (identificacion de API keys:)}

\textbf{Consulte la documentación de la herramienta subfinder y busque las instrucciones
para la configuración después de la instalación. Identifique cuales son las distintas
fuentes de datos que se pueden personalizar con un API key. Seleccione al menos 2
y realice el proceso necesario para obtener un API key gratuita, modifique la
configuración de subfinder para poder usar las API key obtenidas.}

Para esta primera actividad, lo que vamos a hacer es 
configurar las API keys para subfinder, 
donde en este caso vamos a utilizar GitHub y VirusTotal 
esto por que fueron las que mas faciles encontre de acceder, ademas de que en git ya tenia cuenta 
y solo era darle acceso a una mis api keys.

Primero, para sacar la llave de GitHub, 
es necesario ir a la configuración de nuestra cuenta. 
Nos vamos a la sección de Developer settings y 
luego entramos a Personal access tokens (classic).
Ahí le damos en generar un nuevo token. 

\begin{figure}[H]
  \centering
  \includegraphics[width=1.0\textwidth]{img/imagegithub.png}
  \caption{Generación de Personal Access Token en GitHub.}
\end{figure}

Ahora para sacar la ultima api key, 
necesitamos la llave de VirusTotal. 
Para esto es necesario crear una cuenta gratuita 
y una vez logueados, 
nos vamos a nuestro perfil y seleccionamos API key. 

\begin{figure}[H]
  \centering
  \includegraphics[width=1.0\textwidth]{img/imagevirustotal.png}
  \caption{Obtención de API key gratuita en VirusTotal.}
\end{figure}

Ahora bien, para poder meter estas llaves en la 
configuración de subfinder, 
es necesario editar el archivo de configuración 
que se crea por defecto. 
Para esto se utiliza el comando de nano 
en la terminal, donde el comando es el siguiente:

\begin{lstlisting}[style=consolaSeguridad]
nano ~/.config/subfinder/provider-config.yaml
\end{lstlisting}

De hecho con este comando nos damos cuenta de todas las paginas de apis que soporta 
subfinder, donde en este caso nos vamos a enfocar en las de GitHub y VirusTotal, ya que son las que configuramos antes.

\begin{figure}[H]
  \centering

\end{figure}

Al abrir el archivo, directamente lo que vemos es que 
todos los servicios tienen corchetes vacíos \texttt{[]}, 
lo que indica que no hay llaves configuradas.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/image7.png}
  \caption{Archivo provider-config.yaml antes de la configuración.}

Para configurar las llaves, 
tenemos que borrar esos corchetes en las 
entradas de las paginas que obtuvimos las api keys, en este caso 
es de github y virustotal. 
En la línea de abajo debemos poner un guion y nuestra llave.  

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/imageapikeys.png}
  \caption{Archivo provider-config.yaml configurado con las API keys de GitHub y VirusTotal.}

\subsection{Actividad 3: Subdominios asociados a la Facultad de Ingeniería}

\textbf{Analice los resultados obtenidos y determine cuáles son los subdominios que
podrían estar asociados a la Facultad de Ingeniería.}

Ahora bien, para poder filtrar todos los dominios de la unam que 
se quedaron en el archivo anterior, entonces 
para estar tomando de uno en uno, se puede automatizar 
por medio de comandos, donde el comando 
que se tiene que poner en la terminal de Linux es el siguiente:

\begin{lstlisting}[style=consolaSeguridad]
grep -E 'ingenieria\.unam\.mx|fi-[abcp]\.unam\.mx' subdominiosunam.txt > filtrados_fi.txt
\end{lstlisting}

Lo que hace este comando es utilizar 
grep (por la opción -E) para buscar dentro de nuestro archivo 
dos cosas en específico, donde la primera 
tenemos que buscar la plabra de ingenieria,

\subsection{Rangos de IP en formato CIDR:}

\textbf{Indique cuales son los rangos de direcciones IP, usando notación CIDR, que utilizan
los siguientes subdominios:}

\begin{enumerate}
  \item fi-a*
  \item fi-b*
  \item fi-c*
  \item fi-p*
\end{enumerate}

Ahora bien, antes de sacar los rangos completos, lo primero que hicimos fue ver qué dirección IP exacta tenía cada uno de los subdominios que filtramos de la facultad. Para esto armamos un comando en la terminal usando \texttt{awk} y \texttt{dig}, lo que hace que lea nuestra lista, consulte al servidor DNS y nos escupa el dominio junto con su IP en la misma línea.

El comando utilizado fue el siguiente:

\begin{lstlisting}[style=consolaSeguridad]
awk '/fi-[abcp]\.unam\.mx$|\.(fi-[abcp])\.unam\.mx$/{print}' subdominiosunam.txt | sort -u | while read -r host; do ips=$(dig +short A "$host" | sort -u | tr '\n' ' '); [ -n "$ips" ] && echo "$host $ips"; done
\end{lstlisting}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/image9.png}
  \caption{Extracción de direcciones IP individuales para los subdominios (Parte 1).}
\end{figure}

\begin{figure}[H]
  \centering
  \includegraphics[width=0.8\textwidth]{img/image10.png}
  \caption{Extracción de direcciones IP individuales para los subdominios (Parte 2).}
\end{figure}


Ahora bien, para este punto lo que se hace es 
sacar las direcciones IP de los subdominios 
que filtramos anteriormente y 
luego consultar sus rangos de red. 
Como tenemos muchos equipos, esto como lo vimos en clase 
si hicieramos un ping a cada uno a mano no es eficiente, 
por lo que es necesario automatuzarlo, esto 
por medio del siguiente comando:

\begin{lstlisting}[style=consolaSeguridad]
for group in fi-a fi-b fi-c fi-p; do echo "== $group =="; awk -v g="$group" 'tolower($0) ~ g"\\.unam\\.mx$" || tolower($0) ~ "\\." g "\\.unam\\.mx$" {print}' subdominiosunam.txt | sort -u | while read -r host; do dig +short A "$host" | grep -E '^[0-9]+\.' | head -n1; done | awk '{split($1,a,"."); print a[1]"."a[2]"."a[3]".0/24"}' | sort -u; done
\end{lstlisting}

\begin{figure}[H]
  \centering
  \includegraphics[width=1.0\textwidth]{img/image12.png}
  \caption{Ejecución de script en Bash para extraer los rangos de red en formato /24.}
\end{figure}

Donde en este caso, al tener muchos subdominios aunque sea 
de una sola dependencia es el caso de nuestra facultad 
siguen siendo muchos, por lo que 
se hace un ciclo for, donde lo que hace 
es iterar sobre los cuatro grupos principales los cuales son 
fi-a, fi-b, fi-c y fi-p. 

Adentro del ciclo, utilizamos awk que esta se usa mas que nada 
para extraer los subdominios correspondientes a cada grupo. 
Después, pasamos esa lista a un while read 
que le ejecuta el comando dig +short A, donde 
este comando de dig short ya lo utlizamos antes en clase, 
que lo que haces es que lo ejecuta a cada equipo para 
sacar su IP pública, y finalmente, 
usamos otro awk y un sort -u 
para agrupar todas las IPs descubiertas en bloques de red con un prefijo de 24, 
y esto hace que se eliminen los duplicados.

Por lo que la salida, de este comandos nos esta dando los siguientes rangos:

\begin{itemize}
    \item \textbf{fi-a*:} 132.248.54.0/24 y 35.172.49.0/24
    \item \textbf{fi-b*:} 132.248.59.0/24
    \item \textbf{fi-c*:} 132.248.139.0/24
    \item \textbf{fi-p*:} 132.248.52.0/24
\end{itemize}

Por ultimo para poder ponerlos en la notacion 
CIDR, que es la que se nos pide, 
es necesario consultar la base de datos de asignación de IPs. 

Para esto, tomamos una dirección IP representativa de nuestras redes descubiertas, donde en este caso la 132.248.54.121 de thor.fi-a y 
le pasamos el comando whois, filtrando la salida con grep para que nos traiga directamente la línea del bloque CIDR.

\begin{lstlisting}[style=consolaSeguridad]
whois 132.248.54.121 | grep -iE 'cidr|route|inetnum'
\end{lstlisting}

\begin{figure}[H]
  \centering
  \includegraphics[width=1.0\textwidth]{img/image11.png}
  \caption{Consulta WHOIS para confirmar el bloque CIDR principal de la red UNAM.}
\end{figure}

Lo que hace el comando es decirnos 
que todas estas subredes internas \texttt{132.248.X.X} 
en realidad pertenecen a una única de red asignada a 
la universidad, 
que corresponde al bloque CIDR \textbf{132.248.0.0/16}.

Ademas de que, si observamos bien los 
resultados del grupo fi-a, 
notamos una excepción con una IP que empieza con 
35.X.X.X. Si le aplicamos el mismo comando whois 
a esa IP:

\begin{lstlisting}[style=consolaSeguridad]

\subsection{Análisis de los datos generados por la herramienta httpx}

\textbf{Realice un análisis de los datos generados por la herramienta httpx, ¿qué puede
concluir a partir de los datos?}

Por ultimo punto, para estos resultados que se nos dio 
por medio de httpx 
sobre las subredes, las cuales fueron fi-a, 
fi-b, fi-c, 
fi-p, 
toda esta se puede ver como algo un poco 
diversifcada, esto por que de inicio la gran mayoría 
de estos servidores están vivos y responden con 
un código 200 que significa que esta todo OK, 
y nos deja ver algunos de estas paginas 
las cuales son: LIDSOL, Robótica, Computo de Alto Desempeño, o tambien 
plataformas académicas como lo es Moodle. 

También se ven algunas redirecciones 301, 302 y 303, 
además de algunos sitios con errores de gateway que da un codigo de errro de 502 
o que niegan el acceso con el codigo de error de 403, 
lo que indica que existen sistemas de control de acceso configurados.

Ahora bien, yéndonos al análisis de las tecnologías, 
la infraestructura está en casi en su totalidad puesta en 
Apache HTTP Server y Nginx, 
corriendo sobre servidores Linux, de igual forma 
corriendo en
Ubuntu, Fedora, CentOS y Debian, con una única. 
Donde la parte mas importante son las detecciones de 
versiones de software muy desactualizadas 
que ya se encuentran al final de su vida. 

Ademas de que, se detectó el uso de 
aplicaciones web construidas en 
Python, Django, Node.js, Vue.js, CodeIgniter y Java (Apache Tomcat), 
junto con gestores de contenido como WordPress y Moodle.

A partir de los datos, 
podemos decir que aunque la FI cuenta con una red 
interna amplia y funcional, pero 
la falta de actualizaciones regulares 
en sus servicios base (como Apache, PHP y OpenSSL) 
pueden llegar a exitir vulnerabilidad, lo que los vuelve 
de facil acceso si se encuentran mas vulnerabilidades en esos sistemas antiguos.
